Malleable HTML, drawn

How the file and the open page relate, why stripping things out for viewers makes live sync harder, the mistakes that follow, and where each piece of state belongs. The companion to the guide, written for a person or an AI agent about to build one.

1. One file, two forms

A malleable HTML file exists in two forms. The saved file is the bytes on disk. The open page is the live DOM in an editor's browser. ClayJS turns the file into the page when it opens, turns the page back into a file when it saves, and later merges outside changes to the file into the open page.

The difficulty of a malleable file is roughly how different those two forms are. When they are identical, saving and syncing are trivial. Every difference is something ClayJS has to translate in both directions, and it can only translate differences it knows about.

2. The ladder: how much the two forms differ

Pick the lowest rung that fits the file. Each rung up buys a cleaner viewer experience and costs more rules.

3. Why stripping makes sync harder

On rung 1 or 2, an agent's edit to the file and the open page are in the same form, so ClayJS merges like with like. On rung 3 and above they are not. The agent writes the saved form, with no toolbar and inert editing attributes, while the editor's tab holds the live form. ClayJS bridges the gap in two moves before it merges.

Three consequences follow, and they are most of what trips people up:

  • Excluded regions are invisible to sync. ClayJS skips editor-ui, no-save, no-snapshot and freeze regions on every side of a merge. They are never updated by an incoming change. Anything inside them must be rebuilt by your code.
  • Any difference your own code makes is untranslated. If boot code adds a class, a button or an attribute without marking it, that addition is ordinary content. It is saved into the file, viewers receive it, and an outside edit can remove it from the live page.
  • Viewers sync the saved form. A view-mode tab with sync receives the stripped file, never an editor's live page. Its rendered views must also re-render after each update.

4. The mistakes, drawn

Each one is a way the saved file and the open page drift apart in a way ClayJS cannot see.

1. Injected controls without a mark

A script appends an "Add item" button at load. It saves into the file. Next open adds another. Viewers and agents see all of them.

Put clay="editor-ui" on the root of anything created at load, or author the control in the file and hide it by mode (rung 2).

2. Content inside a stripped region

Editor notes go in clay="no-save" so viewers won't see them. They never reach disk, the other editor's tab ignores them, and they vanish on reload.

Stripped regions hold only what can be rebuilt. Notes that editors share are content: keep them in the file and hide them by mode.

3. Startup code that writes defaults

Boot code fills fields from hardcoded values or a JS object. Opening the page overwrites what an agent or another tab put in the file.

Opening must only read. Treat whatever is in the DOM at clay.ready as the truth.

4. Handlers bound once, per element

querySelectorAll('li').forEach(li => li.onclick = …) at load. An item that arrives later by sync, or a node the merge replaced, has no handler.

Delegate: one listener on document that checks event.target.closest(…). It works for every node, present and future.

5. Views that do not re-render

A chart, canvas or parsed JSON object built once at load. Sync updates the record but not the view, and a merged JSON script does not update an object you already parsed.

Write one render() that rereads the record. Call it on load, after local commands, and on clay:sync-applied.

6. Identities that change

IDs generated on every load, or copied when an item is duplicated. The merge pairs the wrong items, so edits land on the wrong row.

Mint an id or data-id once, when the item is created. Keep it through edits and moves. A copy gets a new one.

7. Temporary state on durable elements

A dialog, drag or hover sets a style or class on <body> or a content node. A save during that moment writes it into the file. ClayJS's own crop dialog does this today.

Keep transient state in JS or in an excluded region. Let dialogs close before you export a viewer copy.

8. Hiding treated as privacy

CSS, view mode, viewmode:disabled and hidden inputs change presentation. Anyone who receives the file receives every byte, and editors' tabs exchange snapshots that include no-save content.

Secret data does not go in a file you share. Use a separate file behind its own access, or an explicit clean-copy export you inspect.

5. Where does this piece of state go?

Ask this of every element, attribute and variable as you build. Most files only ever reach the green boxes.

6. The rules

The equivalent of the rules that make React effects predictable. Follow them and saving, syncing and agent edits behave without surprises.

  1. The DOM is the record. If it is work someone would miss, it lives in markup: text, attributes, child order, persisted values, or a merge="store" JSON script.
  2. Opening only reads. Startup code adopts what is in the file at clay.ready. It never writes defaults over it.
  3. Mark every runtime difference. Anything your code adds that should not be saved gets clay="editor-ui" (or another exclusion). An unmarked addition is content.
  4. Stripped regions hold nothing you can't rebuild. Sync never touches them and saving drops them. Recreate them from the record on every load.
  5. One render path. Local commands, undo and incoming sync go through the same reconcile function. Write derived text only when it changed, since writing the same text is still an edit. Bind events by delegation.
  6. Stable identity. Give independently edited items an id or data-id once, keep it forever, and mint a new one for copies.
  7. Hiding is not privacy. Every reader of the file gets every byte. Keep secrets out of shared files.

7. The smallest flat file

Rung 2 in full. Every control is in the file, viewers get the same bytes with the controls hidden, and an agent can edit any of it on disk.

<!DOCTYPE html>
<html lang="en" autosave>
<head>
  <meta charset="utf-8">
  <title>Tasks</title>
  <style>html:not([editmode="true"]) [show-when\:editmode="true"] { display: none }</style>
</head>
<body>
  <h1 editmode:contenteditable inert-contenteditable="plaintext-only">Tasks</h1>
  <ul id="tasks" sortable="tasks">
    <li data-id="t-1"><span show-when:editmode="true" sortable-handle>↕</span> <span editmode:contenteditable inert-contenteditable="plaintext-only">Write the brief</span></li>
  </ul>
  <button show-when:editmode="true" type="button" data-action="add">Add task</button>
  <template id="task-tpl">
    <li><span show-when:editmode="true" sortable-handle>↕</span> <span editmode:contenteditable contenteditable="plaintext-only">New task</span></li>
  </template>

  <script src="https://clayjs.com/v1/clay.js?plugins=sync,sortable,indicator&exclude=richclay"></script>
  <script src="https://clayjs.com/v1/clay-options.js"></script>
  <script>
    document.addEventListener("click", (event) => {
      if (!event.target.closest('[data-action="add"]') || !clay.isEditMode) return;
      const li = document.getElementById("task-tpl").content.firstElementChild.cloneNode(true);
      li.dataset.id = "t-" + Date.now().toString(36) + Math.random().toString(36).slice(2, 6);
      document.getElementById("tasks").append(li);
    });
  </script>
</body>
</html>

Note what it does not need: no editor-ui, no render function, no clay.ready wait. Three details carry the weight. The record is written in its saved form (inert-contenteditable), so a viewer gets plain text from the very first open, while the <template> holds the live form because a clone is inserted while someone is editing. New items come from the template, never from a copy of a live item, and get a fresh data-id built without crypto.randomUUID, which is missing on plain http. And the click handler checks clay.isEditMode, because hidden buttons are still in a viewer's page. Move to rung 3 only when viewers must receive HTML without the controls; examples/skeleton.html is that next step, with undo, a filter and a computed summary.

clay-options.js turns each show-when: attribute into one CSS rule in a <style data-name="option-visibility"> tag. That tag is saved with the file, so after the first save a viewer's browser hides the controls from the first paint. Before the first save the rule exists only once the script runs, which is why the file carries its own fallback rule, html:not([editmode="true"]) [show-when\:editmode="true"] { display: none }. Key it on :not([editmode="true"]): the saved file has no editmode attribute at all, so a rule on editmode="false" never matches before boot. The same attributes work for any state, not just editing: view="kanban" on an ancestor with show-when:view="kanban" or hide-when:view="kanban" below it.
