A visual guide to malleable documents

ClayJS is a script tag that makes a plain HTML file save its own edits back into itself. There is no separate database and no build step: the HTML file is both the application and the record.

Section 1The save loop: one file in two forms

In a traditional web app, HTML is a disposable view rendered from a database. In a malleable document, the HTML file is the database. When a user edits text, checks a box, or reorders a list, those changes happen directly in the DOM, and saving writes the updated HTML document back over the file it came from.

To build with ClayJS without bugs, hold one core distinction in mind: the document exists simultaneously in two forms.

  • The saved file (bytes on disk): What a visitor or an AI agent reads. It must be complete and accurate before any JavaScript runs: every heading, list item, checked box, and saved total is plain HTML markup.
  • The open page (live DOM in a browser tab): What an editor interacts with. It contains the saved record plus temporary runtime additions: floating formatting toolbars, drag handles, filter inputs, selection highlights, and ClayJS's own state attributes on <html>.

Here is what happens on each half of the loop:

  1. Opening the file: When a host serves the file to an authorized editor (via a savetoken attribute on <html> in HTML Clay, or the owner cookie on Hyperclay), ClayJS sets editmode="true" and pageowner="true|false" on <html>, activates mode-specific attributes, mounts editing plugins, and waits 500 ms of quiet (up to 3 s) before taking its clean baseline snapshot and setting savestatus="saved".
  2. Saving the page: Triggered by <html autosave> (debounced 1.5 s after your last edit, at most 10 s during continuous typing), Cmd+S / Ctrl+S, a click inside [trigger-save], or calling clay.save(). ClayJS clones the entire document, copies live values from persist controls into attributes, deletes every clay="editor-ui", no-save, and no-snapshot subtree, converts active mode attributes back to their inert saved form, strips root runtime attributes (editmode, pageowner, savestatus, savetoken, documentetag), and sends the HTML string to POST /_/save. With the default source plugin enabled, ClayJS pairs unchanged elements to their original source byte ranges so only modified elements are reprinted.

Section 2Editors, viewers, and form state

A malleable document is one file shared by both its author (in edit mode) and any visitor (in view mode). You do not build a separate read-only page. Instead, you use four mode attributes, declarative visibility, and form persistence so the saved file is safe and read-only by default, and becomes interactive only when ClayJS enters edit mode.

1. The four mode attributes

ClayJS ships exactly four mode attributes. On save, a transform writes their inert form into the file; on load in edit mode, ClayJS activates them:

  • editmode:contenteditable renames contenteditable to inert-contenteditable on save (preserving its value, such as "plaintext-only") and restores contenteditable in edit mode.
  • editmode:onclick renames onclick to inert-onclick on save and restores it in edit mode.
  • editmode:resource on <script>, <style>, or <link> prefixes type with inert/ on save and strips the prefix in edit mode so the resource runs.
  • viewmode:disabled and viewmode:readonly add disabled or readonly in the saved file and remove them in edit mode.

Crucial distinction: Author existing records in the file in their saved form (inert-contenteditable="plaintext-only", disabled), but write blueprints inside <template> in their active form (contenteditable="plaintext-only", no disabled), because templates are cloned while editing and save transforms do not reach inside <template>.

2. Hiding controls & persisting inputs

Showing and hiding controls: Load clay-options.js and put show-when:editmode="true" on edit-only buttons and drag handles. Because the saved file has no editmode attribute on <html> until ClayJS boots, always include this one-line fallback in your <style> block so viewers never see edit controls flash on first load:

html:not([editmode="true"]) [show-when\:editmode="true"] {
  display: none;
}

Persisting form controls (persist): In browsers, typing into an <input> or checking a checkbox changes a live DOM property (.value, .checked), not the HTML attribute. Without persist, saving serializes the old attribute and loses the user's input. Put persist on every record <input>, <textarea>, and <select> so ClayJS mirrors live values into value, checked, and selected attributes on input and before every snapshot.

Section 3Regions and ephemeral state: what gets saved and what does not

Every element in an open malleable document belongs to one of three categories: Record (the durable work), Chrome (editing UI and navigation), or Derived (counts, totals, and projections computed from the record). Almost every bug in a malleable app happens when chrome or derived state leaks into the saved record.

You control that boundary with two mechanisms: the clay attribute on regions (subtrees), and the ephemeral attribute on individual saved elements.

Section 5Live sync, agents, and three rules that prevent drift

When you load ?plugins=sync, every open copy of the file stays in step through a save-gated, three-way DOM merge. Whether a collaborator saves in another browser tab or an AI agent edits the .htmlclay file directly on disk, the host pushes the new HTML frame to your open tab and ClayJS merges it into your live page without a reload.

Follow these three rules and the file on disk, your open page, and every collaborator or agent will never drift apart:

Rule 1 · Mark everything your code adds

Unmarked DOM mutations are treated as document edits and written into the file on the next save.

  • Author static edit buttons in the file with show-when:editmode="true".
  • Put script-created UI and derived views inside a clay="editor-ui" container cloned from a <template>.
  • Use clay.ephemeral.toggle(el, "selected") or a runtime stylesheet inside editor-ui for tab-local state, never plain classes or inline styles on records.
What goes wrong without it

Duplicated controls: A script appends an unmarked toolbar at load. Saving writes it into the file, and the next load appends a second copy.

Leaked UI state: Clicking a card adds .selected or hidden. That class autosaves, adds an undo step, and selects or hides the card for every collaborator.

Rule 2 · Adopt the DOM on load, and reconcile on change

The live DOM is the single source of truth, and sync or undo can change it under your script at any time.

  • Never rewrite the record at boot. Guard your script with if (window.__appStarted) return;.
  • Give every repeated item a unique data-id when created or cloned so sync pairs items reliably.
  • Delegate events on document, re-render derived views on clay:sync-applied, and re-sync .checked / .value from attributes on clay:sync-applied, undo, and redo.
What goes wrong without it

Lost or doubled items: Two tabs add items without data-id, or a clone keeps the original's data-id; sync cannot pair them.

Stale controls after undo: Undo restores the checked or value attribute, but the browser still displays the old property and writes it back on the next save.

Rule 3 · The saved file is what people share

Every byte in the saved file is downloaded by everyone who can view the document, and nothing outside the file survives a reload.

  • Notes or settings meant to persist for editors belong in the record (hidden from viewers with show-when:editmode="true"), not in no-save.
  • Hiding with CSS, hidden, or show-when: is presentation, not access control. Keep confidential data in a separate file with restricted access.
What goes wrong without it

Vanishing notes: An editor's scratch notes are placed in no-save or editor-ui; they disappear on the first reload.

Exposed secrets: Private numbers or API keys hidden with show-when:editmode="true" are still readable by any viewer in View Source.

Section 6State decision map and complete starter file

When adding any element, attribute, or variable to a ClayJS app, trace it through this decision tree:

The smallest complete Rung 2 file, line by line

This 30-line HTML file is a complete task list you can check off, rename, add to, and drag to reorder. It needs zero custom JavaScript: its controls live in the file and hide in view mode (Rung 2).

<!DOCTYPE html>
<html lang="en" autosave>
<head>
  <meta charset="utf-8">
  <title>Tasks</title>
  <style>html:not([editmode="true"]) [show-when\:editmode="true"] { display: none }</style>
autosave on <html> saves 1.5 s after edits settle. The <style> rule hides show-when:editmode="true" controls from viewers before any script loads (the backslash escapes the colon in CSS, and :not([editmode="true"]) matches the saved file where editmode is absent).
</head>
<body>
  <h1 editmode:contenteditable inert-contenteditable="plaintext-only">Tasks</h1>
editmode:contenteditable activates editing for the owner and saves as inert-contenteditable="plaintext-only" so viewers get plain text from the very first open.
<ul id="tasks" sortable="tasks">
sortable="tasks" makes list items draggable in edit mode by their sortable-handle grip and saves the new child order as HTML.
    <li data-id="t-1"><span show-when:editmode="true" sortable-handle>↕</span> <input type="checkbox" persist viewmode:disabled disabled> <span editmode:contenteditable inert-contenteditable="plaintext-only">Write the brief</span></li>
  </ul>
Each item has a unique data-id so sync and drag-and-drop can identify it. The checkbox uses persist so checking it writes a checked attribute into the file, and viewmode:disabled disabled so viewers cannot toggle it.
  <button show-when:editmode="true" type="button" add-from="#task-tpl" add-to="#tasks">Add task</button>
add-from and add-to require no JavaScript: clicking in edit mode clones #task-tpl into #tasks, stamps a fresh data-id on the new <li>, and focuses its editable text.
  <template id="task-tpl">
    <li><span show-when:editmode="true" sortable-handle>↕</span> <input type="checkbox" persist viewmode:disabled> <span editmode:contenteditable contenteditable="plaintext-only">New task</span></li>
  </template>
Blueprints inside <template> are written in their active form (live contenteditable, no disabled) and carry no data-id, because they are cloned while editing and each copy receives a fresh id.
  <script src="https://clayjs.com/v1/clay.js?plugins=sync,sortable,indicator&exclude=richclay"></script>
  <script src="https://clayjs.com/v1/clay-options.js"></script>
</body>
</html>
sync merges external and peer edits, sortable enables drag reordering, indicator shows the save status chip, and exclude=richclay skips the rich-text editor since every field here is plain text. clay-options.js compiles show-when:editmode="true" into CSS.

Try it yourself: Save those lines as tasks.htmlclay and open the file in HTML Clay (or upload it to Hyperclay). Click Add task, rename the item, check the box, and drag it above "Write the brief". Once the indicator says Saved, inspect the file in a text editor: your new item, its checked attribute, and the new order are all plain HTML on disk, with only one Add task button.
